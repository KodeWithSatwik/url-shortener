# ADR-001: Short Code Generation Strategy

**Status**: Accepted
**Date**: Phase 1

## Context
We need to generate short, unique codes (6–8 characters) for each shortened URL. Options considered:
1. **Base62 of auto-increment DB ID** — encode the entity's primary key in Base62 (a-z, A-Z, 0-9)
2. **Random Base62** — generate random 6-char string, check for collision
3. **MD5/SHA hash prefix** — take first 6 chars of URL hash
4. **NanoID** — cryptographically random, URL-safe

## Decision
**Base62 encoding of auto-increment ID.**

## Rationale
- **No collision by design**: each ID is unique; encoding it produces a unique code. No retry loop needed in the happy path.
- **Predictable length growth**: 6 Base62 chars cover 56 billion codes (62^6). Adding a 7th char scales to 3.5 trillion. No reconfiguration needed for a long time.
- **Simple, auditable**: easy to decode back to the original row for debugging.
- **No external randomness dependency**: no UUID generation, no random seed concerns.

## Trade-offs
- Short codes are sequential (code N+1 is predictable from code N). This is acceptable for a URL shortener where enumeration is not a meaningful attack — the full URL is the secret, not the code.
- Requires the DB to assign the ID before the code is known. A two-step pattern is needed: insert with a placeholder or use the returned ID.

## Alternatives Rejected
- **Random Base62**: requires collision check on every insert; at scale collision probability rises.
- **Hash prefix**: different URLs can produce the same 6-char prefix (genuine collision, not just probability).
- **NanoID**: overkill; sequential IDs are simpler and sufficient.
