# ADR-005: Rate Limiting Strategy

**Status**: Accepted
**Date**: Phase 1

## Context
Without rate limiting, the API is vulnerable to abuse (mass URL creation, redirect flooding).

## Decision
**Bucket4j in-memory token bucket, applied per-IP via a Jakarta Servlet filter.**

## Rationale
- **Bucket4j**: the standard Java token bucket library. Lightweight, no external dependency, integrates cleanly with Spring.
- **Token bucket**: allows short bursts while enforcing average rate. Better user experience than fixed window.
- **Per-IP**: prevents a single client from exhausting shared capacity.
- **Jakarta Servlet filter**: applied before Spring MVC, so rejected requests don't consume Spring thread resources.

## Configuration
- Default: 20 requests/minute capacity, refills 20 tokens every 60 seconds.
- Configurable via `app.rate-limit.*` in `application.yml`.

## Trade-offs
- **In-memory only**: rate limit resets on restart. Counters are not shared across JVM instances — horizontal scaling requires replacing this with Redis + Bucket4j's Redis integration. Documented as a known limitation.
- **Per-IP only**: no per-user or per-API-key rate limiting in Phase 1 (added in Phase 6 with user management).
- **No distributed rate limiting**: acceptable for a single-instance prototype.

## Alternatives Rejected
- **Spring Cloud Gateway rate limiter**: requires deploying a gateway — too heavy for this prototype.
- **Fixed window counter**: poor burst handling; token bucket is standard.
- **No rate limiting**: not acceptable for a production-grade demonstration.
