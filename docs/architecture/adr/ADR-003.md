# ADR-003: Analytics Storage

**Status**: Accepted
**Date**: Phase 1

## Context
We need to store click events for analytics. Options:
1. Same relational DB (new `click_events` table)
2. Separate analytics DB (ClickHouse, TimescaleDB)
3. In-memory counters only (no event history)

## Decision
**Same relational database, separate `click_events` table.**

## Rationale
- **Simplicity**: no additional infrastructure for a prototype. One DB connection, one Flyway migration set.
- **Sufficient for demo scale**: PostgreSQL handles millions of rows in a `click_events` table without issue.
- **Async write**: analytics are recorded asynchronously via `@Async`, so redirect latency is not affected by the DB write.

## Trade-offs
- At very high click volumes (billions of events), a dedicated time-series DB (TimescaleDB, ClickHouse) would be more appropriate. This is documented as a known limitation.
- Analytics queries (top referrers, time-series aggregations) are simple GROUP BY queries — no window functions needed at this scale.

## Alternatives Rejected
- **Separate analytics DB**: overkill for a prototype, adds operational complexity.
- **In-memory counters only**: loses event history, cannot reconstruct analytics after restart.
