# ADR-002: Database Choice

**Status**: Accepted
**Date**: Phase 1

## Context
We need a relational database to store shortened URLs and click events.

## Decision
- **Development / Test**: H2 in-memory
- **Production**: PostgreSQL 16

## Rationale
**H2 (dev/test)**:
- Zero setup — no Docker, no install required to run or test the project.
- Flyway-compatible: same migration scripts run on H2 and PostgreSQL.
- Fast test cycles: in-memory means no disk I/O.

**PostgreSQL (prod)**:
- ACID compliant, proven at scale.
- Excellent support for JSON columns (future analytics enrichment).
- Supported by Spring Boot and Hibernate natively.
- Widely available on cloud platforms (AWS RDS, GCP Cloud SQL, etc.).

## Trade-offs
- H2 SQL dialect differs slightly from PostgreSQL. Flyway migrations are written in ANSI SQL to remain dialect-neutral; H2 compatibility mode (`MODE=PostgreSQL`) is not needed for this schema.
- Not using MySQL/MariaDB: PostgreSQL has better standards compliance and JSON support.

## Alternatives Rejected
- **MySQL**: License considerations, slightly worse standards compliance.
- **MongoDB**: URL shortener is fundamentally relational (foreign keys, constraints). No document flexibility needed.
- **Redis as primary DB**: Redis is excellent for caching redirect lookups but not suitable as the sole persistence layer for this prototype.
